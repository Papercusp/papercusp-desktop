A **kickoff** is a curated, task-specific system-prompt brief layered on top of the engineer-collaborator playbook when the operator UI spawns a power-user agent session. The button that launches the session names a *kind*; the server writes the matching brief into a temp file and hands its path to the `psu` launcher via `--launch-context=<path>` (P-032). `psu` parses `--launch-context` itself and appends the brief to the **raw** agent CLI — `--append-system-prompt-file` for claude, `--append-system-prompt` for omp, and per-session `CODEX_HOME/AGENTS.md` materialization for codex. The engineer playbook and superuser MCP are assembled by `bootstrap-su` / `buildLaunchSpec` per launch; the `*-su` wrappers (`claude-su` / `omp-su` / `codex-su`) are retired. The launched session opens already framed for the task.

Per [`plans-newbutton-and-subharness-scope-2026-05-25`](/internal/docs/plans/plans-newbutton-and-subharness-scope-2026-05-25), kickoffs ride the launch-context / system-prompt channel — they are not first-user messages. This keeps them in scope for the whole conversation and matches the existing engineer-collaborator brief and PTY feature-pi brief.

## Built-in kinds

| Kind        | Brief                                            | Launched from                          |
| ----------- | ------------------------------------------------ | -------------------------------------- |
| `new-plan`  | `apps/operator/prompts/kickoffs/new-plan.md`     | "New plan" button on PlansClient (`/adv/plans` + `/admin/plans`) |
| `feature`   | Inline-rendered from `harness_features` row       | PTY feature-pi spawn (in-app TUI pane) — uses the same factory but doesn't ride the launch route |

The `feature` kind is *not* in the launch-route allowlist — it's only reachable through the in-process PTY spawn path, where the harness/feature ids are already authenticated.

## Adding a new kickoff kind

Three small edits:

1. **Author the brief.** Drop a markdown file at `apps/operator/prompts/kickoffs/<kind>.md`. Plain prose; if you need server-supplied context (e.g. an active harness slug) reference it as `{{harness_context}}` (or invent a new placeholder) and substitute in the renderer.

2. **Add a body renderer.** In `packages/operator-core/lib/agent-kickoff/prompt-file.ts`, extend the `KickoffKind` type and the `KickoffCtx` discriminated union with the new kind, then add a `renderXxxBody(ctx)` function dispatched from `renderKickoffBody`. For brief-file kinds the renderer just `readFileSync`s the curated MD (from `apps/operator/prompts/kickoffs/`) and stamps in the context. For data-driven kinds (like `feature`) the renderer builds the body from PG / files.

3. **Allowlist the kind.** In `packages/operator-core/lib/agent-kickoff/kickoff-kind.ts`, add the kind to `KICKOFF_KIND_ALLOW` (the allowlist + `validateKickoffKind` validator moved here from the retired `console-launch` route in P-032). The kickoff launch now rides `packages/operator-core/lib/endpoint-route/routes/adv/launch-su.ts`, which calls `validateKickoffKind` and `buildKickoffPromptFile`, then hands the file to `psu` via `--launch-context`. `psu` appends it to the raw agent CLI itself (no `*-su` wrapper).

The launch refuses any kind not in `KICKOFF_KIND_ALLOW`; the brief body is curated in-repo and never accepted as a free-text payload (D-003).

## What gets emitted on the wire

The `psu` argv (`launch-su.ts`) ends up shaped like:

```
psu --no-picker --agent=claude --harness=<slug> --no-plan \
  --launch-context=/dev/shm/papercusp-kickoff-aBcDeF/new-plan.md \
  --role=planner
```

A new-plan kickoff always appends `--role=planner` (launch-su.ts:164) — the launched session *is* the Planner role/persona, so the dock panes it as a typed Planner pane (and the deferred row records `role: 'planner'` for the same reason).

The `--agent=` token reflects the **configured backend** (claude unless `/settings/agent` overrides it) — `--agent=omp` would just be one such pick. The New-plan button sends *no* agent, so the route resolves it via `effectiveBackend(readAgentConfig())` (launch-su.ts:77-78), following the global setting rather than a hardcoded value.

Since WI-1282 (su-context-size-variants), the route also accepts an optional `context_size: 'full' | 'trimmed'` in the launch body, validated by `isSuContextSize` and forwarded as `--context-size=<full|trimmed>` on the `psu` argv (right after `--model=`, before `--resume-session=`). Omitted ⇒ no flag is passed and each client (`claude`/`codex`/`omp`) keeps its own native default. This is orthogonal to kickoffs — it sizes the *superuser tool catalog* the session boots with, not the kickoff brief.

The New-plan button launches with `defer_spawn: true` (PlansClient.tsx:662). Instead of spawning an OS terminal, the server records a pending `adv_sessions` "workbench launch" row carrying this same argv as `launchArgv`, then wakes the pui dock-driver — which reactively opens a pane that *runs* the launcher (launch-su.ts:155-181). The `exec psu …` form below is the non-deferred terminal path:

```
exec psu --no-picker --agent=claude --harness=<slug> --no-plan \
  --launch-context=/dev/shm/papercusp-kickoff-aBcDeF/new-plan.md \
  --role=planner
```

`psu` resolves the engineer playbook + coord wiring itself per agent (via `bootstrap-su` / `buildLaunchSpec`); the kickoff file rides `--launch-context`. On the terminal path every token is run through `shellEscape` so whitespace in the temp dir name survives. The brief file is GC'd 30 seconds after creation (`setTimeout(..., 30_000)` in `prompt-file.ts`) — long enough for the launcher to read it, short enough that it doesn't accumulate.

## Why a separate system-prompt brief, not a first-user message

A first-user message would mingle with the user's actual input and get trimmed first under context compaction. The system-prompt channel frames the whole session — "you are a plan-creation interviewer" stays in scope after the user replies, and the engineer-collaborator brief is already there with the same shape.

See [`plans-newbutton-and-subharness-scope-2026-05-25`](/internal/docs/plans/plans-newbutton-and-subharness-scope-2026-05-25) decisions D-001 (system-prompt channel) and D-002 (shared factory) for the full reasoning.
