14. Plugin marketplace — design proposal (v1, post-review-round-2)

Status: historical design record — superseded by the in-app Cupboard

This page is the original design rationale for a standalone plugin marketplace. The plugin distribution model it proposes (a kind discriminator on papercusp.json, install-time capability consent, per-harness enable, the actions primitive, lockfiles) has shipped — but the storefront is now the in-app Cupboard (apps/operator-public = @papercusp/cupboard-worker, a Cloudflare Worker + D1, live at cupboard.papercusp.com), not a papercuspai.com/marketplace/ site. The Cupboard is a single catalog with four listing kinds — plugin (install), blueprint (fork), snapshot (fork), and harness (join) — exposed over HTTP (/api/cupboard/*), with no cupboard:* MCP verbs. Plugins install to ~/.papercusp/global-plugins/<slug>/ and mount under /api/plugins/<name>/. Treat the URLs, package names (papercusp-marketplace, papercusp-plugin-sdk), and ~/.papercusp/installed/ paths below as the historical proposal’s wording, not current identifiers; the concepts map onto the Cupboard. Read this for the why; see the authoring quickstart for the how today.

14.0 Why this exists

Section titled “14.0 Why this exists”

The marketplace today distributes harness templates — reusable recipes that spin up concrete harness instances (papercup-coding, papercup-org). They ship with their own roles, model preferences, and project layout.

But templates can’t share integrations. If papercup-coding wants “one-click publish to Cloudflare Pages”, that integration is either baked into the template (forcing every coding harness in the world to know about Cloudflare) or has to be implemented separately by every template author. Same for vscode-server, Slack notifications, Postgres schema management, etc.

This is why every mature plugin ecosystem has a plugin marketplace distinct from a theme/template marketplace: WordPress separates plugins from themes; VS Code separates extensions from project templates; Backstage separates plugins from app shells.

Papercusp needs the same split. Templates are recipes; plugins are horizontal capabilities that any template can pull in.

The two failure modes to avoid

Section titled “The two failure modes to avoid”
  1. Obsidian / WordPress’s “no sandbox” — host trivially exploitable by malicious or buggy plugin. Both retroactively bolted on capability prompts.
  2. Backstage’s “build-time only” — installs require rebuild + redeploy. Backstage 2.0 is rebuilding the plugin model around runtime loading.

Papercusp’s spec already commits to: iframe sandboxing for v2 UI plugins (Figma’s model), runtime install with capability consent (Chrome Web Store style), capability strings at the DI boundary (VS Code × Cap’n Proto). This proposal builds on that foundation.

14.3 The four design pillars

Section titled “14.3 The four design pillars”

14.3.1 Reuse the marketplace pipeline; add a kind discriminator

Section titled “14.3.1 Reuse the marketplace pipeline; add a kind discriminator”

papercusp.json adds:

papercusp publish is kind-agnostic. The catalog stores kind in the package row. The marketplace site filters at /marketplace/?kind=template|plugin (default both). Search and authors all work without code changes.

papercusp install checks the kind:

  • template → registers in ~/.papercusp/registry.json (already implemented)
  • plugin → unpacks to ~/.papercusp/global-plugins/<slug>/ (already implemented in plugin-loader); the substrate’s plugin-runtime mounts on next papercusp run

Both flows go through the same publish + signing + retraction infrastructure. Operators get the same ops dashboard counts. Authors see “5 templates and 12 plugins published” on their profile.

14.3.2 Plugin lifecycle: install-time consent, harness-time mount

Section titled “14.3.2 Plugin lifecycle: install-time consent, harness-time mount”

A plugin is installed once globally — capability-consent prompt at that point. Then mounted at runtime into every harness instance whose template requires it (or that the user enables via papercusp plugin enable cloudflare-pages --harness sheets-clone).

This matches WordPress’s “active plugins per site” + Backstage’s “plugins mounted into the app”.

14.3.3 New primitive: actions (button-shaped, presence-determined runtime)

Section titled “14.3.3 New primitive: actions (button-shaped, presence-determined runtime)”

The current SDK has hooks, routes, UI, routines, schema. Missing: a user-triggered action that the harness UI can surface as a button.

Runtime is presence-determined:

  • serverHandler only → server runtime (Node-only, full DI, capability-checked)
  • clientHandler only → client runtime (iframe, postMessage RPC, network-bound capabilities)
  • Both present → hybrid (substrate routes preview to client, commit to server)
    • v1 rejects manifests with both at load time, with a clear not-yet-implemented: hybrid actions error
    • v1.5 lifts the rejection — no manifest schema change at any point

This pattern mirrors VS Code’s contributes.commands (declarative) + commands.registerCommand (imperative). It avoids the “function in JSON manifest” trap and keeps a clean migration path to iframe sandboxing.

Three properties make actions worth their own primitive vs reusing routines/hooks:

  1. They’re user-discoverable. A button in the dashboard. Routines and hooks are invisible to the end user.
  2. They have parameters. A “Publish” button needs to know the target. JSON-schema → auto-form.
  3. They have execution status. Async with a progress indicator. Routines fire-and-forget; hooks are passive.

WordPress has admin actions, VS Code has commands, Slack has slash commands, Backstage has Actions Catalog. We need our equivalent.

14.3.4 Capability consent UI at install time

Section titled “14.3.4 Capability consent UI at install time”

Adapted from Chrome Web Store / iOS App Store consent screens, using the capability tiers we already have (§10.6.1). The first line names what kind of artifact is being installed (plugin vs template) so users understand the runtime implications.

14.3.5 Capability granularity — per-id everywhere

Section titled “14.3.5 Capability granularity — per-id everywhere”

All UI capabilities are per-id, matching the per-id collision-resolution rule from §10.5. A plugin claiming ui:dashboard-tab:foo can mount one tab named foo; mounting bar requires a separate ui:dashboard-tab:bar capability.

This makes the consent prompt name what’s actually being claimed:

CapabilityWhat it grants
ui:dashboard-tab:<id>One tab in the dashboard tab strip
ui:sidebar-item:<id>One sidebar entry in the harness chrome
ui:harness-action:<id>One action surface (button, menu item)
ui:harness-route:<slug>One full-route mount under /harness/<slug>
ui:plugin-config-panelOverride the auto-generated config form (see §14.3.7)

The previous coarse ui:dashboard-tab (no id) was proposed for removal here. In the shipped SDK, the coarse no-id forms (ui:dashboard-tab, ui:sidebar-item, ui:harness-route, ui:tui-pane) are what landed — the per-id capability granularity in this section is design intent, not the current Capability type.

14.3.6 Server-runtime resource isolation

Section titled “14.3.6 Server-runtime resource isolation”

Server-runtime action handlers run as Node code inside the substrate process. The iframe sandbox (§10.4) does not apply. To prevent one plugin from degrading the whole harness:

  • Per-action timeout — defaultTimeoutSec on the action (default 30s); substrate cancels via AbortSignal threaded through ctx.signal.
  • No process:spawn capability in v1 — see §14.3.6.1 below.
  • Soft heap budget — substrate polls process.memoryUsage() per harness; if a plugin’s RSS jumps >256 MB above its baseline during a handler call, the action is cancelled and the harness logs a budget violation.
  • Postgres connection cap — plugin’s ctx.db proxy holds at most one connection per concurrent action invocation; long-running queries get the same AbortSignal as the action.

14.3.6.1 No process:spawn capability in v1

Section titled “14.3.6.1 No process:spawn capability in v1”

A process:spawn capability — even per-binary (process:spawn:git) — is unsafe. Common binaries have config flags that spawn other binaries (git -c core.fsmonitor=<attacker-binary> is the canonical example; the same trick works for ssh, docker, npm, node). Per-(binary, args-pattern) capabilities would re-implement sudoers, which is not a thing we want to maintain.

Instead, follow the architecture §10 already commits to: every capability resolves to a method on a substrate-provided typed service. Apply the same posture for subprocess needs:

  • v1 has no process:spawn capability.
  • The substrate offers typed wrappers for the common cases: git: GitService, docker: DockerService, shell: { execTrustedCommand(name: TrustedBinary, args) } where TrustedBinary is a substrate-curated enum.
  • Plugins that need a binary that isn’t wrapped → contribute an SPI extension upstream, or live without it in v1.

process:spawn can be revisited in v1.5 if real plugins prove the typed-service approach insufficient. Don’t lead with the foot-cannon.

14.3.7 paramsSchema / configSchema dialect commitment

Section titled “14.3.7 paramsSchema / configSchema dialect commitment”

Every place this proposal says “UI auto-generates a form” needs a precise contract or it silently degrades to “we ship a generic form, every serious plugin overrides it” (the WordPress experience).

Commitments:

  1. Dialect: JSON Schema Draft 2020-12, strict subset:

    • Allowed: object, array, string, number, boolean, enum, oneOf for tagged unions
    • Allowed: format for email, uri, hostname, date-time, uuid
    • Disallowed: $ref to external URIs (security + offline use); if/then/else; not; additionalProperties: <schema>
    • Disallowed: regex pattern containing backreferences (ReDoS class)

  2. Companion uiSchema sibling using RJSF’s vocabulary (widgets, hints, ordering). Optional. Plugin author writes:

  3. Escape hatch — ui:plugin-config-panel capability: plugins that need full control register their own React component for the config UI. The substrate calls into it via the iframe-bridge (or directly in v1 trusted server-runtime case).

This is what Backstage and VS Code arrived at after years of “auto-form” debt. Spec it now.

14.5 Existing tab classification — what should be plugin vs core?

Section titled “14.5 Existing tab classification — what should be plugin vs core?”

The current papercusp dashboard has 8 tabs: proposals, dashboard, summary, docs, vscode, pi, insights, config. Each needs a classification: keep in core, or extract to a plugin?

The principle: a tab is core if every harness — coding, research-org, content-pipeline, marketing-bot, anything — would benefit from it. A tab is a plugin if it’s specific to one template family or external integration.

TabToday’s contentRecommendedRationale
dashboardFeature queue, agents, logs, issues — the main canvasCOREThis IS the harness UI. Every harness has features+agents+logs. Plugins contribute INTO it via dashboardTabs/sidebarItems. If this were a plugin, harnesses with no plugins would have nothing to show.
summaryHigh-level changelog of what’s been builtCOREGeneric across all templates. A research-org harness wants “what got researched”; a content-pipeline wants “what got published”; coding wants “what features shipped”. Same primitive.
insightsFeatures count, cost, tokens, iterationsCOREUniversal harness metrics. Every harness pays for tokens; every harness has iterations.
configPer-instance configurationCOREEvery harness needs config. Plugins contribute their own config sections via configSchema.
proposalsAI-generated scope expansion suggestions for the SPEC.mdCORE for v1, defer extractionSee §14.6 — proposals isn’t a UI tab extraction, it’s an authorization-model question.
docsiframe of project docs (fumadocs on :4325)PLUGIN (@papercupai/fumadocs)Optional integration with an external docs server. Templates that don’t generate docs shouldn’t see this tab.
vscodeiframe of code-server on the project dirPLUGIN (@papercupai/vscode-server)Code-server is heavyweight + only useful when there’s code to edit. Research, marketing, support harnesses don’t need it.
piiframe of the pi (omp) interactive coding agentPLUGIN (@papercupai/pi-companion)Pi is one specific external tool. Would be like baking “ChatGPT side panel” into Slack.

Where this proposal disagrees with the maintainer’s initial take

Section titled “Where this proposal disagrees with the maintainer’s initial take”

The maintainer suggested:

  • Core: pi, insights, Config
  • Plugins: proposals, dashboard, summary, docs, vscode

This proposal disagrees on three of them:

  1. dashboard should stay CORE, not become a plugin. The dashboard is the composition surface — it’s where plugins’ actions and tabs render. Making it a plugin would mean “harness with no plugins = empty UI” which breaks the first-run experience and the “core works without plugins” guarantee.
  2. summary should stay CORE. Every harness benefits from “what got done”; the implementation is template-agnostic (read features+goals from state, render a timeline). Pulling it into a plugin would force every template author to either reimplement it or depend on the same plugin (a tax on adoption).
  3. pi should be a PLUGIN, not core. Pi/omp is one specific external tool; not all harnesses use it. Treating it as core would tie papercusp to one external tool.

The dashboard nuance: the dashboard chrome (tab strip, panel layout, action surfaces) stays core. The dashboard’s primary panel (feature queue for coding ≠ briefing pipeline for research-org) is contributed by the active template via a defaultDashboardPanel UI contribution. Templates ship their own dashboard panel; the chrome stays core.

  • Plugins are loaded at substrate boot; existing harnesses see them on next papercusp run
  • Templates that haven’t been republished still work (they just don’t get the new tabs until users explicitly install the plugins)

14.8 Tradeoffs

Section titled “14.8 Tradeoffs”
  • vs. Backstage’s build-time-only: we pay for runtime loading with the iframe sandbox v2 work and per-instance config UI. Worth it — the marketplace pitch needs runtime install.
  • vs. WordPress’s full-trust plugins: we pay for the capability system with manifest verbosity and consent friction. Worth it — we won’t have an Obsidian-style retroactive cleanup.
  • vs. VS Code’s command system: we collapse “commands” + “API contributions” into one actions primitive. VS Code distinguishes because their plugins do many non-action things (language servers, decorations, etc). Our plugins are smaller-surface; one primitive suffices.
  • vs. Slack’s hosted apps: we run plugins on the user’s substrate, not on our infrastructure. The capability sandbox makes this safe-ish; it also means plugins can do things hosted ones can’t (read project files, work offline).
  • actions vs reusing routines: distinct surfaces, single trigger registry. Actions = user-clicked buttons (with parameters, status UI). Routines = scheduled/event-fired (cron, webhook, substrate event). A routine that targets an action (targetAction: 'publish') is the same code path as the user-clicked action, with trigger-source differing in the audit row.
  • No process:spawn capability in v1: plugins that need subprocess access use typed substrate services or contribute upstream. Trade flexibility for safety; lift in v1.5 if proven necessary.

14.9 Resolved decisions

Section titled “14.9 Resolved decisions”

These were open questions in the v1 draft and resolved through review.

14.9.1 Plugin scope: per-machine install + per-harness enable

Section titled “14.9.1 Plugin scope: per-machine install + per-harness enable”

Plugins are installed once globally (papercusp install <slug>). They’re enabled per harness instance via papercusp plugin enable. This matches every comparable system (VS Code, WordPress active-plugins-per-site, Backstage).

14.9.2 Granted-capabilities scope: per-(plugin, version, harness-slug) with sticky extension

Section titled “14.9.2 Granted-capabilities scope: per-(plugin, version, harness-slug) with sticky extension”

The decision: strict per-(plugin, version, harness-slug) as the default. Sticky “extend to other harnesses” affordance at second-use.

Concrete consent flow:

  1. First grant (e.g. secrets:read:CLOUDFLARE_API_TOKEN for harness sheets-clone): one prompt, granted for sheets-clone only. Recorded in granted-capabilities.json as {plugin: 'cloudflare-pages', version: '0.1.0', harness: 'sheets-clone', cap: 'secrets:read:CLOUDFLARE_API_TOKEN'}.

  2. Second grant of the same cap from a different harness (e.g. enabling the plugin on random-research-spike): the prompt now offers two buttons:

    • Grant for this harness only — adds harness: 'random-research-spike' row
    • Grant for all current and future harnesses on this machine — wildcards the harness slug (harness: '*'); future harnesses re-evaluate without re-prompting

  3. Update with new capability (e.g. plugin v0.2.0 adds secrets:read:CLOUDFLARE_PAGES_API_TOKEN): per §10.8 update flow, prompt for the new capability only; existing grants survive.

This gives strict isolation by default (no silent cross-harness leakage), one prompt for the common case (one-harness-per-plugin), and an explicit opt-in for the convenience case.

Three alternatives considered + rejected:

  • Uniform per-machine (simplest, every plugin marketplace does it) — accepts that secrets installed for harness A are usable by harness B on the same box.
  • Uniform per-(plugin, version, harness-slug) with a “remember for all” checkbox at first prompt — one consent surface; the high-cost case is the explicit unchecked default.
  • Tier-graded scope (low per-machine, medium per-(machine, plugin, version), high per-(machine, plugin, version, harness-slug)) — three different scope semantics is too much complexity to ship without two consent surfaces designed first.

The chosen path balances safety (strict default) and friction (one-prompt common case) without inventing new prompt surfaces.

14.9.3 Default dashboard panel ownership

Section titled “14.9.3 Default dashboard panel ownership”

Templates contribute their default dashboard panel via a defaultDashboardPanel UI contribution in the template’s manifest. Render order: template’s panel first; plugins’ tabs appended.

14.9.4 First-party vs community parity

Section titled “14.9.4 First-party vs community parity”

@papercupai/* plugins get prominence (verified badge, default ranking) but no extra capabilities. Same security model for everyone.

14.9.5 Forwards-compatibility with iframe sandbox v2

Section titled “14.9.5 Forwards-compatibility with iframe sandbox v2”

The action handler’s runtime location is explicit in the manifest via serverHandler / clientHandler presence (§14.3.3). Plugin authors don’t rewrite anything when the iframe sandbox lands; the loader resolves to the right execution path based on what’s in the manifest.

14.9.6 Lockfile retraction interaction

Section titled “14.9.6 Lockfile retraction interaction”

Three retraction states map to three lockfile behaviors:

StateAuthor intentLockfile reaction
deprecated”still works, prefer X going forward”Warn at papercusp run, proceed normally
withdrawn”I removed this, but please don’t break grandfathered installs”Warn loud at papercusp run, require --allow-withdrawn flag to actually run
quarantined”this version is actively unsafe — security issue or supply-chain compromise”Refuse to run, force papercusp upgrade-pin <plugin> to bump to next non-retracted version

Same rules apply to recommends entries: a recommends pointing at a quarantined plugin is stripped from the suggestion UI entirely (not shown with a warning).

14.9.7 Lockfile transitivity

Section titled “14.9.7 Lockfile transitivity”

The rule: every line in the lockfile is something the user explicitly chose to be in their world.

  • Hard requires are pinned transitively in the lockfile (npm/cargo behavior). The plugin author tested against a specific dep version; surprises are bugs.
  • recommends are NOT in the lockfile until the user accepts them. Once accepted, they enter the lockfile and pin transitively from then on (the recommended plugin’s own requires get pinned).
  • An un-accepted recommends showing up after a template version bump re-prompts but doesn’t pin until acceptance.

This invariant makes lockfiles legible to humans, which matters more for a marketplace than for npm.

14.9.8 recommends UX touch-points

Section titled “14.9.8 recommends UX touch-points”
  • CLI: papercusp install <template> shows the recommends list with --with-recommends (default off) and --no-recommends flags
  • Web admin: modal at template-install completion with checkboxes
  • Re-evaluation: on papercusp run if the lockfile shows recommends mismatching the current template version, prompt; on a template version bump, the install flow re-shows the recommends diff
  • Persisted state: track which recommends were “skipped” so we don’t keep re-asking (~/.papercusp/skipped-recommends.json)

14.10 Plugin → plugin dependencies

Section titled “14.10 Plugin → plugin dependencies”

Both requires and recommends are valid at both template and plugin manifest levels:

Resolution at install time:

  1. Substrate computes the transitive closure of requires
  2. Substrate prompts user for capability consent for ALL plugins in the closure
  3. If any plugin in the closure is quarantined, refuse install; if any is withdrawn, require explicit override
  4. On install, all transitive requires enter the lockfile (per §14.9.7)
  5. recommends from the leaf packages are surfaced separately (per §14.9.8) and not pinned until accepted

This matches VS Code’s extensionDependencies + extensionPack semantics. The retraction-aware install flow (§14.9.6) applies uniformly to all plugins in the closure.
