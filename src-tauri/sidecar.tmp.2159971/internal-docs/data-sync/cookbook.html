Zero is being retired — historical reference

Zero / zero-cache / ZQL named-queries / WebSocket push is on the retirement path. The shipping desktop app uses SSE-primary sync (the :3070 Hono host pushes invalidate/update over Postgres LISTEN/NOTIFY); zero-cache is not run on desktop. Treat this page as historical reference. Source of truth: apps/operator/providers/HarnessZeroProvider.tsx (transport-selection doc-comment) + the root CLAUDE.md deployment-model section.

Migration:

Steps in order:

  1. Add import { RichGrid, type ColumnDef } from '@papercusp/grid-core'.
  2. Build a columns array, one entry per visible field. Wrap in useMemo.
  3. Replace the .map() block with <RichGrid …>.
  4. Move per-row click handler from each row to onRowClick.
  5. Drop the manual loading + error CSS (RichGrid renders its own header even when rows is empty; provide a sibling empty-state component if you need a friendlier message).

Recipe 3: Adding a new column to an existing Zero-synced table

Section titled “Recipe 3: Adding a new column to an existing Zero-synced table”

For each existing harness, repeat. Then:

  1. Update bin/scaffold-harness-schema.sh so future harnesses get it.
  2. Update libs/zero-harness/src/schema.ts — add new_col: string() (or the right type — beware TIMESTAMPTZ).
  3. The publication already includes the table; the new column flows automatically.
  4. Restart zero-cache-harness.
  5. Update consumers (useSyncQuery results now include new_col).

Recipe 6: Mutations that update Zero panels

Section titled “Recipe 6: Mutations that update Zero panels”

You want a button that inserts a row and have every connected client see it appear.

The API route writes to PG. Zero broadcasts. useSyncQuery re-renders. Done.

If you want optimistic UI before the round-trip, hold the new row in component state and clear it when the Zero query result reflects the real one. Don’t try to write through Zero — that’s not how this stack works.

Recipe 9: PG-mirrored filesystem store

Section titled “Recipe 9: PG-mirrored filesystem store”

Use this when a filesystem JSON file must remain authoritative — e.g. an external CLI writes it, or a runtime loader reads it by path — but you also want cross-harness queries and Zero subscriptions over the same data.

The pattern in three parts:

1. The PG table is a derived index of the JSON. Same schema, plus updated_at. Add to the zero_harness publication.

2. A mirror helper. Reads the JSON for one harness/scope, upserts matching rows, deletes orphans. This is the function every writer calls.

3. Hook every writer. After each successful JSON write — direct or via subprocess — call the mirror. Best-effort: a mirror failure logs but does not fail the API call.

4. Backfill + drift recovery. Provide a script that reads ALL JSONs and re-syncs PG. It runs on a fresh checkout, after a direct CLI run that bypassed the operator API, or whenever you suspect drift.

When to pick this pattern over PG-canonical

Section titled “When to pick this pattern over PG-canonical”
Pick PG-canonical (Recipe 1-2) whenPick PG-mirror (this) when
You own every writerA third-party process or runtime path writes the JSON and you can’t change it
The data has no on-disk consumerA loader reads the JSON file at runtime by path
Atomicity of write mattersThe JSON is the operational source of truth and PG is a query-side index
