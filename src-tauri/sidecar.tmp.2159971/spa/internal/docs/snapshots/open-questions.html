Open questions and V1/V1.1/V2 split

Rounds 2–6 review feedback incorporated

Six review rounds have shaped this list. The V1 set has grown from the original ~1,500 LOC estimate to ~2,000–2,100 LOC honest as defensive features (PG lock, bwrap smoke test, helper library, security advisory consultation, key-rotation attestation) have been folded in. The V1 launch criterion has also been reframed: “vetted-publisher alpha” not “public marketplace launch” — the latter requires the moderation layer covered in V1.1+.

Send sign-off reviewers to the sign-off checklist at the bottom.

V1 launch criterion: “shippable to a vetted-publisher alpha where the worst a malicious vetted-publisher can do is fail at the consent gate or be sandboxed.” Anything that fails to meet that criterion is V1; anything that improves the system but isn’t a security or correctness gate is V1.1+.

Public marketplace launch is V1.1+, gated on the moderation layer.

V1 — gates “safe to release to a vetted-publisher alpha”

Section titled “V1 — gates “safe to release to a vetted-publisher alpha””

Idempotency, safety, sandboxing

Section titled “Idempotency, safety, sandboxing”
ItemWhy V1
Idempotency contract: done-marker hashes (configHash, scriptHash, pluginVersion); aliases for renames + null for removals; structural fields default to forcing re-provision; skipReprovisionOnPatch governs pluginVersion only, never scriptHashRe-runs silently corrupt state; edits to region/accountId orphan resources; a malicious patch with same major.minor and skipReprovisionOnPatch: true cannot slip through because the script-hash always forces re-consent
Sandbox by default for all scriptsWithout it, build scripts are an unconditioned arbitrary-code-execution vector for any approved publisher (npm event-stream / xz-utils precedent). Signing proves provenance, not safety.
Linux: bwrap with bundled binary + install-time smoke testBundled bwrap covers distro variance; smoke test catches kernels with disabled unprivileged user namespaces. Failure → permanent sandbox_available: false → signed-only mode for substrate’s lifetime
macOS: sandbox-exec + signed-only mode (no unsigned scripts at all)sandbox-exec is deprecated but functional — meaningful boundary against accidents. Refusing unsigned scripts on macOS plugs the “unsigned + no real sandbox” gap
Network policy floor: 169.254.0.0/16, 127.0.0.0/8, 10/8, 172.16/12, 192.168/16, ::1, fd00::/8 always blocked, regardless of allowedHosts or cloudProviderCloses IMDS-credential exfiltration and lateral-movement attack classes
cloudProvider: { id, region } presets with monthly signed update channel + region templatingReplaces the old network: "open" mode which gave plugins effectively unbounded outbound network access. Per-region presets close the cross-region leak surface.
Static-analysis warnings on common destructive patterns (curl | bash, sudo, rm -rf $HOME, eval of untrusted input, chmod -R 777, base64-blob-smuggle)Cheap and high-signal; catches “I copy-pasted destructive command and didn’t notice” failure mode

Trust, signing, and consent

Section titled “Trust, signing, and consent”
ItemWhy V1
Trust granularity per-(publisher, plugin) keyed on signing-key fingerprintCoarser-grained trust silently gives @publisher’s malicious new plugin the same trust as their existing benign one
Ownership transfer invalidates trust — different publisher_id on a new version triggers fresh consentCloses the xz-utils-in-miniature attack class
Key rotation events must be marketplace-countersigned”Publisher rotated their key, re-trust?” prompt is otherwise a phishing surface; without marketplace’s infrastructure-key signature the prompt is just trust-me-bro-from-attacker
Quarantine clears trust for the affected (publisher, plugin). Publisher-key compromise advisory clears all of (publisher, *)Cached trust must die when marketplace flags anything bad
papercusp plugin install --dev path with per-machine ad-hoc signing key + dev: true trust flagPlugin authors can iterate on macOS / signed-only platforms without publishing each save to a marketplace

Section titled “Recovery, lifecycle, observability”
ItemWhy V1
PG-backed harness_shared.operator_claims for setup locking with PG advisory locks + heartbeat-renewed expires_atFile-based locks don’t survive multi-machine harness sharing (laptop ↔ desktop split-brain)
papercusp_record_resource <kind> <id> helper that writes to state.json immediatelyPlugin authors aren’t infra engineers; partial-failure rollback should not require defensive idempotency-handling logic in setup.sh
Recovery contract: stale-lock detection prompts cleanup before re-trying setup; partial-failure offers automatic teardown of recorded resourcesKilled/crashed setup leaves undiagnosable orphan resources
Teardown contract: plugin’s teardown.sh is the dispatcher; receives recorded resource list via state.json and dispatches per kindLocks Path 1 explicitly so plugin authors don’t ship empty teardown.sh assuming substrate magic
OAuth ctx.oauth.token(field) helper with pre-emptive refresh + 401 retry-once + Promise-cache for concurrent-refresh stormEvery plugin reinvents refresh logic poorly; offline-laptop case produces inscrutable failures; concurrent calls without Promise-cache race the provider’s refresh endpoint
PAT scope introspection (V1 GitHub)Hybrid-mode pastes silently produce under-scoped tokens that break action handlers at runtime

Sign-off checklist

Section titled “Sign-off checklist”

Before V1 implementation begins, these need explicit sign-off:

  • V1 list above is the full set — anything in V1.1 that should actually be V1?
  • V1 line-count target (~2,000–2,100 LOC) is realistic
  • Sandbox-by-default for all scripts is the locked design
  • bwrap bundling + install-time smoke test — substrate ships its own copy
  • macOS: signed-only mode + sandbox-exec, no unsigned-script path in V1
  • PAPERCUSP_DEV_UNSIGNED=<sha256> + papercusp plugin install --dev is the only macOS dev escape
  • Network policy floor (IMDS + RFC1918 + loopback) always blocks, regardless of allowedHosts or cloudProvider
  • cloudProvider presets with region templating + monthly signed update channel
  • Trust per-(publisher, plugin) keyed on signing-key fingerprint
  • Ownership transfer invalidates trust
  • Key-rotation events marketplace-countersigned
  • Cost field dropped from V1; budget enforcement comes via real budgetCap helper in V1.1
  • Audit retention defaults (1y / 50MB cap) + auditLogCapMb per-plugin override + fail-loud on encrypted-locked volumes
  • aliases covers both renames and removals
  • versionPin: { mode: "exact" } is the reproducible default (legacy pluginVersionPinned: true maps to it); security advisories prompt loudly at fork
  • runAt: "first-action" synchronization contract (action returns setup-required; hooks queued + replayed; webhooks 503’d) is the locked design
  • Default for structural-vs-operational fields is structural
  • papercusp_record_resource helper + plugin’s teardown.sh as dispatcher
  • PG-based operator_claims lock (not file-based) for multi-machine fork safety
  • who-based shared-host detection + one-time acknowledgement banner
  • Vetted-publisher allowlist process documented as part of V1 launch criterion
  • arctic adoption gated on supply-chain audit; rolled-our-own is the fallback
  • Phasing: share-semantics + OAuth ship in one PR; build-scripts in a second PR
  • V1.1 follow-up list is acceptable as fast-follow

Once these are checked, implementation begins. The order is:

  1. PR 1 (~600 LOC): Snapshot share-semantics + OAuth substrate + GitHub provider + ctx.oauth.token() helper + paste-PAT scope check + version pinning (versionPin) + security-advisory consultation
  2. PR 2 (~1,400–1,500 LOC): Build-script lifecycle (manifest, runner, sandbox with bwrap-bundling + smoke test, audit, recovery via PG, consent flow, cloudProvider presets, network floor, trust per-(publisher, plugin) with rotation/transfer, hook queue-and-replay, single-user-host detection, helper library) + dogfooded against the existing cloudflare-pages-hosted Worker deploy
  3. PR 3 (V1.1 onward): github-repo refactored to use build scripts + runAt scheduling + budgetCap + AWS-Budgets helper + skip-teardown banner + marketplace moderation layer (separate spec)

Long-tail design questions

Section titled “Long-tail design questions”
  1. secret: true implying shareable: false? Round-1 reviewer said keep separate. Standing.
  2. Array-shaped configs (apiKeys: [...]) — fine to require named-field objects.
  3. .shape.json location — next to the redacted config.
  4. PKCE for OAuth — defense-in-depth, V1.1.
  5. OAuth client_secret storage — V1 supports both clientSecretFile (0600) and env-var.
  6. Concurrent setup for multi-plugin snapshots — V1 sequential; parallel: true opt-in deferred.
  7. state.json resource validation — V1 trusts the script; plugin authors build into verify.

These will be answered as the implementation surfaces them; none gate V1 sign-off.
